# Agent Documentation System — Developer Guide

This guide explains the documentation infrastructure built into this repo for Claude Code agents.
It is written for developers, not agents — agents use the skills and CLAUDE.md files directly.

---

## What This Is

Nestfolio is a ~33-service, 4-domain monorepo. The breadth of its architecture (EventBridge,
DynamoDB CDC, Step Functions, Angular MFEs, CDK, 4 domains with their own event buses) makes
it difficult for an AI agent to stay consistent across conversations. Without guidance, agents
invent conventions, miss constraints, and produce code that looks plausible but violates the
patterns the rest of the codebase depends on.

This system solves that with three things: a smart router (root CLAUDE.md) that's always loaded
and acts as a traffic controller, a library of skills loaded on demand for specific tasks, and
auto-derived service cards that describe every service from code. Together they give agents
exactly the right context at the right time — not a giant doc dump at the start of every
conversation.

---

## How It Works

Three mechanisms work together:

**Root CLAUDE.md (always loaded).** Claude Code loads this automatically in every conversation.
It stays under ~2KB and does exactly three things: gives a compact system mental model, routes
every task type to the correct skill, and states the hard constraints agents must never violate
(no inter-service API calls, event-processor pipelines on all Lambda handlers, tests in `test/`).

**Skills (on demand).** Skills live in `.claude/skills/` as directories with a `SKILL.md` file
each. Claude Code auto-discovers them and loads them on demand — either when you invoke them
directly (`/skill-name`) or when Claude determines they match the current task based on the
skill's `description` frontmatter. Skills reference code — they don't duplicate it. When a skill
loads, it tells the agent what to read, not what to paste.

**Sub-agents (verification).** The `verify/` skills dispatch isolated sub-agents using Claude
Code's `Agent` tool. This keeps audit work out of your main conversation context. A sub-agent
audits a service, writes its report, and returns — your conversation only sees the summary.

## Cognitive Layers

The system is organized into four layers with different load costs:

```
┌─────────────────────────────────────────────────────┐
│ L0 — ALWAYS LOADED                                  │
│ Root CLAUDE.md (~2KB)                               │
│ System mental model + skill routing + hard rules    │
├─────────────────────────────────────────────────────┤
│ L1 — ON DEMAND (system/ skills)                     │
│ orient.md         → full system understanding       │
│ domains.md        → domain boundaries + event map   │
├─────────────────────────────────────────────────────┤
│ L2 — ON ACTION (implement/ skills)                  │
│ create-service, create-feature, create-event,       │
│ create-data-flow, create-mfe, cdk-patterns,         │
│ event-processor-patterns, testing-patterns          │
├─────────────────────────────────────────────────────┤
│ L3 — AUTO-DERIVED (generated, never authored)       │
│ services/{domain}/{svc}/CLAUDE.md → service card    │
│ Generated by audit-service skill from code          │
└─────────────────────────────────────────────────────┘
```

**L0** is the only constant cost. It's always loaded, always small.

**L1** is for orientation — loaded when an agent needs to reason about the system broadly or
understand how domains interact.

**L2** is for doing — loaded when an agent is about to take a specific action. L1 and L2 are
independent; an agent working on a single service feature doesn't need L1.

**L3** is auto-derived. Service cards are generated from code by `audit-service` and stored at
`services/{domain}/{svc}/CLAUDE.md`. The routing table and implement/ skill checklists enforce
that agents read the relevant service card as their first step before modifying anything. Note:
Claude Code does NOT auto-load CLAUDE.md files from arbitrary nested directories — L3 cards are
loaded explicitly by the skill checklists.

## Skills

All 21 skills are in `.claude/skills/`, each in its own directory with a `SKILL.md` file.
Claude Code auto-discovers them and lists their descriptions in the system prompt so it can
invoke them automatically when a task matches. The routing table in CLAUDE.md reinforces this.

### system/ — Orientation

| Skill | What it does |
|-------|-------------|
| `orient` | Full system map on demand: domains, services, libs, frontend, infra, deployment |
| `domains` | Domain boundaries, EventBridge buses, events produced/consumed, adapter forwarding rules |

### implement/ — Action

| Skill | What it does |
|-------|-------------|
| `create-service` | End-to-end guide: Nx generator → CDK stack → pipeline handlers → tests → service card |
| `create-feature` | Checklist for adding a feature to an existing service |
| `create-event` | Define TypeScript schema → register → CDC or explicit emit → adapter rules → consumer updates |
| `create-data-flow` | Design, implement, and document a cross-domain event flow |
| `create-mfe` | MFE conventions, routing, BFF integration, shared UI components |
| `cdk-patterns` | 5-construct pattern reference: State, Ingress, Egress, Facade, AgentRuntime |
| `event-processor-patterns` | Pipeline types, handler structure, DLQ config, test harnesses |
| `testing-patterns` | Directory convention, unit vs integration, harnesses, naming |

### verify/ — Verification

| Skill | What it does |
|-------|-------------|
| `audit-service` | Verifies a single service: structure, naming, handler patterns, tests, import boundaries, card freshness |
| `audit-domain` | Verifies a full domain: service completeness, adapter forwarding, event contract consistency |
| `audit-system` | Full system sweep via parallel sub-agents; produces a dashboard |
| `ci-audit` | CI-optimized audit scoped to `nx affected` projects; structured output for PR comments |
| `init-docs` | Nuclear rebuild — regenerates all service cards, validates all flows, full audit sweep |

### flows/ — Flow Specifications

| Skill | What it does |
|-------|-------------|
| `generate-flow-spec` | Traces an end-to-end business flow through code and produces the `.flow.yaml` spec |
| `validate-flow` | Reads a `.flow.yaml` spec and verifies each step against actual code |
| `impact-analysis` | Scans all flow specs to assess the blast radius of an event rename or service change |

### architect/ — Design Reasoning

| Skill | What it does |
|-------|-------------|
| `design-service` | Structured framework for designing a new service: domain ownership, boundaries, events, state shape |
| `design-data-flow` | Framework for designing a cross-domain flow: trigger, hops, failure modes, idempotency |
| `generate-c4-diagrams` | Compiles D2 source into navigable C4 SVG diagrams with AWS icons and drill-down links |

Both architect skills invoke the `superpowers:brainstorming` skill as their first step, then
layer Nestfolio-specific questions on top. After a design is approved they hand off to
`superpowers:writing-plans`.

## Service Cards

Every service has an auto-generated CLAUDE.md at `services/{domain}/{svc}/CLAUDE.md`. These are
L3 in the cognitive hierarchy — generated from code, never hand-edited.

**Format:**
```markdown
# {service-name}

Domain: {domain} | Bus: {domain}Bus
Stack: services/{domain}/{service}/cdk/service.stack.ts

## State
- {TableName} (DynamoDB, streams enabled|disabled)

## Ingress
- {Bus} → {service}-ingress (SQS → Lambda)
  Subscriptions: {EVENT_1}, {EVENT_2}, ...

## Egress
- CDC: DynamoDB Streams → {service}-egress (Lambda)
  Emits: {EVENT_1}, {EVENT_2}, ...

## Step Functions
- {SFName}: {one-line description}

## Dependencies
- libs: {lib1}, {lib2}, ...
```

No prose. Structured facts only. The format is intentionally compact so agents can load it as
context without burning tokens on narrative.

**Regeneration.** Every implement/ skill ends with a step to invoke `audit-service`, which
regenerates the card. The CI pipeline also regenerates stale cards automatically and commits
the result. You can manually regenerate any card with:

```
/audit-service {service-name}
```

**Never edit service cards manually.** Any change you make will be overwritten on the next
audit. If the card content is wrong, the source of the problem is the code — fix that, then
regenerate.

## Flow Specs

Flow specs are machine-readable YAML files that describe end-to-end business flows. They live
in `flows/` at the repo root.

**Current flows (10):**
- `investor-onboarding.flow.yaml`
- `deposit.flow.yaml`
- `withdrawal.flow.yaml`
- `advisory-cycle.flow.yaml`
- `order-execution.flow.yaml`
- `portfolio-rebalance.flow.yaml`
- `order-ledger.flow.yaml`
- `reconciliation.flow.yaml`
- `market-data-ingestion.flow.yaml`
- `go-live.flow.yaml`

**Schema (see `flows/SCHEMA.md` for full reference):**
```yaml
schema_version: 1
flow: order-execution
description: Route a trade order from advisory approval through broker execution
domains: [advisory, execution, ledger]
trigger: execution-ctrl emits ORDER_CREATED

steps:
  - service: execution-hub
    receives: ORDER_CREATED
    via: ExecutionBus → SQS → execution-hub-ingress
    state_change: Order record written to ExecutionTable
    emits: ORDER_ROUTED (CDC)
    idempotent: true

  - service: broker-ctrl
    receives: ORDER_ROUTED
    via: ExecutionBus → SQS → broker-ctrl-ingress
    state_change: BrokerOrder record created, Step Function started
    emits: ORDER_SUBMITTED (CDC)
    idempotent: false

success_criteria:
  - Order status is FILLED in ExecutionTable
  - Ledger event TRADE_SETTLED received by ledger-hub

failure_modes:
  - step 2 fails: broker-ctrl DLQ → alert; SF handles retry via Wait state
```

**Generating a new spec.** Don't write flow specs by hand. Run:
```
/generate-flow-spec {flow-description}
```
The skill traces actual event subscriptions, CDC configurations, and adapter forwarding rules
from code to produce the YAML. Review the output before committing — the agent may miss edge
cases that need manual annotation.

**Validating.** After any change to services involved in a flow:
```
/validate-flow {flow-name}
```
This checks every step against real code and reports broken links with `file:line` references.

## C4 Architecture Diagrams

The repo includes a D2-based C4 model that renders navigable SVG diagrams with clickable
drill-down: C1 (system) → C2 (domain) → C3 (AWS resources per service).

**Source files:**
- `docs/architecture/nestfolio.d2` — root file with global classes (AWS icons), C1/C2 layers, and layer imports
- `docs/architecture/c3/{service-name}.d2` — one C3 diagram per service (5-construct CDK pattern)
- `docs/architecture/icons/` — AWS service SVG icons referenced by D2 classes

**Generated output:**
- `docs/architecture/nestfolio/` — navigable SVGs (never edit directly)

**Generation script:** `tools/generate-c4-diagrams.mjs`

The script does three things in one pass:
1. Compiles `nestfolio.d2` via the d2 CLI (renders all layers including C3 sub-diagrams)
2. Adds `.svg` extensions to the extensionless files d2 produces
3. Patches navigation hrefs so drill-down links resolve to `.svg` files

Run it with:
```bash
node tools/generate-c4-diagrams.mjs
```

**When to regenerate:**
- After modifying any `.d2` file in `docs/architecture/`
- After creating a new service (add a C3 file + wire the layer import in `nestfolio.d2`)
- As part of `/init-docs` (full rebuild)

**Adding a C3 diagram for a new service:**
1. Create `docs/architecture/c3/{service-name}.d2` following the 5-construct template in the `generate-c4-diagrams` skill
2. Add `c3-{service-name}: { ...@./c3/{service-name}.d2 }` to the domain's `layers:` block in `nestfolio.d2`
3. Add `link: layers.c3-{service-name}` to the service node in the C2 layer
4. Run `node tools/generate-c4-diagrams.mjs`

**Important:** Never render C3 files standalone (`d2 c3/foo.d2`) — the AWS icon classes are
defined in the parent `nestfolio.d2` and won't be available. Always render from the root file.

## Verification Pipeline

There are three layers of verification:

**Pre-commit hook** (`scripts/verify-structure.sh`). Runs in ~3-8 seconds with no API calls.
Scoped to services with staged changes. Checks:
- `project.json` exists with required targets
- `src/service.stack.ts` exists
- `test/` directory exists
- No imports from `services/` (only `libs/`)
- Service name follows `-ctrl`, `-bff`, `-hub`, `-adpt`, or `-web` suffix convention
- Service card (CLAUDE.md) exists (warning only, non-blocking)
- Shows `nx affected` blast radius for the staged changes

**CI GitHub Action** (`.github/workflows/pr-audit.yml`). Runs on every PR using
`claude-sonnet-4-6` (cost-efficient for convention checking). Scoped via:
```bash
pnpm nx affected --base=origin/main --head=HEAD --select=projects
```
This catches transitive dependencies — a change to `libs/event-processor` correctly flags all
services that depend on it. The audit runs `audit-service` per affected project, `validate-flow`
for flows touching changed services, and `impact-analysis` if events changed. Results are posted
as a PR review comment. If the Claude API is unreachable, the check is marked **skipped** (not
failed) — it never blocks a PR due to API outage. Estimated cost: ~$0.05-0.15 per PR.

**Interactive audits** (during development). Invoke any of these on demand:

```
/audit-service {service-name}    # verify a single service + regenerate its card
/audit-domain {domain-name}      # verify all services + adapter rules in a domain
/audit-system                    # full sweep, parallel sub-agents per domain
```

The verify/ skills dispatch sub-agents — your main conversation context only sees the summary.
A full `audit-system` runs 4 parallel sub-agents (one per domain), each of which runs N
sub-agents for their services.

## How to Add a Skill

1. Create a directory in `.claude/skills/your-skill-name/` with a `SKILL.md` file

2. Add the required frontmatter:
   ```markdown
   ---
   name: your-skill-name
   description: One-line description — Claude uses this to decide when to load the skill automatically
   ---
   ```

3. Write the skill body following this structure:
   ```markdown
   ## When This Skill Applies
   [Precise trigger conditions]

   ## Prerequisites
   [Other skills or knowledge needed first]

   ## Checklist
   1. [ ] Step one
   2. [ ] Step two
   ...
   N. [ ] Regenerate service card (invoke audit-service)

   ## Reference Files
   - `libs/event-processor/src/pipelines/` — pipeline implementations
   [Points to code paths, never pastes code content]

   ## Anti-Patterns
   - NEVER do X because Y
   ```

4. Register the skill in the routing table in root CLAUDE.md. Add a row to the `| Task | Skill |`
   table mapping the task description to your skill name.

A few things to keep in mind:
- Every implement/ skill should end with a step to regenerate the service card
- Skills point to code paths — they don't paste code. Use `## Reference Files` for this
- The `## Anti-Patterns` section is mandatory. This is where tribal knowledge lives
- Verify/ skills should dispatch sub-agents to keep audit output out of the main context

## How to Add a Flow Spec

Don't write flow YAML by hand. Invoke the generator:

```
/generate-flow-spec {flow-name or description}
```

The skill will:
1. Ask you to describe the trigger event and the expected end state
2. Trace the flow through actual event subscriptions, CDC configurations, and adapter rules
3. Produce a `.flow.yaml` file in `flows/`

After generation:
- Review the output — the agent traces code mechanically and may miss compensating flows or
  retry logic that isn't visible from subscriptions alone
- Run `/validate-flow {flow-name}` to confirm every step links to real code
- Commit both the YAML and any corrections

## Full Rebuild

After a major refactor — renaming services, restructuring domains, changing event naming
conventions — all service cards and flow specs will be stale. Use:

```
/init-docs
```

This runs a nuclear rebuild:
1. Regenerates service cards for all services
2. Re-runs `generate-flow-spec` for all flows (producing diffs against current specs)
3. Regenerates C4 architecture diagrams from D2 source
4. Runs `audit-system` to verify everything
5. Reports any issues that require manual resolution

Plan for it to take a few minutes and require a review pass before committing.

## Common Audit Findings

These are the issues that show up most often in `audit-service` reports:

**Import boundary violation.** A service is importing from `services/` instead of `libs/`.
Services must be fully isolated — all shared code lives in `libs/`. Move the shared code to
the appropriate lib and update the import.

**Missing `test/` directory.** The project has a `src/` directory but no `test/` directory.
This usually means tests were created in `src/__tests__/` (the Jest default). Move them to
`test/` — see the `testing-patterns` skill for the correct structure.

**Handler without pipeline.** A Lambda handler exists but doesn't use an event-processor
pipeline. This is a hard failure. Every Lambda in this codebase goes through a pipeline;
this is how RequestContext, error handling, DLQ routing, and observability work. See the
`event-processor-patterns` skill.

**Stale service card.** The service's `CLAUDE.md` card doesn't match the current code — a
subscription was added, a table was renamed, etc. This is an auto-fix: `audit-service` will
regenerate it. If you're seeing this in CI it means a recent PR modified the service without
triggering a card regeneration.

**Service card missing entirely.** A new service was scaffolded but `audit-service` was never
invoked. Run `/audit-service {service-name}` to generate the initial card.
