# Backlog system review — /backlog-next-epic + worker refactor

> **Provenance:** multi-agent (ultracode) adversarial review, 2026-06-21 — 8 dimension reviewers
> + per-finding verification (56 agents). Tally: 28 confirmed, 2 needs-decision, 12 by-design,
> 5 false-positives.
> **Disposition:** all **5 majors** + the cheap should-fixes were addressed on branch
> `feat/backlog-next-epic-orchestrator` before merge (see the design spec's
> "Post-review refinements" section and the fix commit). The two `--auto`/picker decisions were
> resolved with the user (strict pause + advisory floor; index exclusion + worker guard).
> Pre-existing out-of-scope nits (rule-3 anchors in code blocks; parking-member-of-shipped-epic
> invisibility) are left for a follow-up backlog item.

## Verdict
Not safe to merge as-is. The core feature set is well-designed and the `epic-members.mjs` resolver is clean, dependency-light, and well-tested — but four confirmed coherence defects break load-bearing capabilities the orchestrator advertises: epic resume crashes, the one-PR invariant leaks via a downstream sub-skill, the batched-e2e gate has no failure path, and `--auto` can't actually override blocking prompts raised inside sub-skills. The flat-section picker can also grab an epic member directly, bypassing the orchestrator. Fix the four majors plus the picker-redirect gap; the rest are minors/nits and a few genuine user-decision calls.

## Must-fix before merge (confirmed-real, ordered by severity then blast radius)

### 1. Resume (E9) collides with unconditional E2/E3 — re-invoking a half-run epic hard-fails
**Where:** `backlog-next-epic/SKILL.md` E2 (lines 52–56), E3 (61–71), E9 (146–148) — dimension: orchestrator-completeness.
**Why:** The procedure is strictly single-pass with no resume gate. E2 unconditionally runs `git worktree add -b feat/epic-<id> …` (no existence guard) → "branch/path already exists" on every resume. E3 unconditionally `Write`s the run-state JSON, clobbering the state E9 says it should *read*. E9 thrice-promises "re-enters the worktree, continues at the next open member," but nothing implements it — an agent executing top-to-bottom crashes at E2. (The finding's claimed E0 preflight failure is *not* a reliable mechanism — a live worktree is non-stale and resume from main passes — so the real crash is E2 + silent E3 state loss.)
**Fix:** Add a resume gate at the top of the Procedure: if `<git-common-dir>/backlog-next-epic-<id>.json` exists → skip E1 promotion, make E2 idempotent (`git worktree list | grep -q epic-<id> || git worktree add …`; `git rev-parse --verify feat/epic-<id> || …`), and have E3 read-if-exists rather than overwrite. Jump to E4.

### 2. executing-plans → finishing-a-development-branch fires inside epic-member mode, breaking the one-PR invariant
**Where:** `backlog-next/SKILL.md` Step 5 routing (84–91) + Epic-member delta 6.7/6.8 (173); `superpowers:executing-plans` Step 3 — dimension: epic-flow-trace.
**Why:** Worker line 176 says "Step 5 downstream routing runs unchanged"; Step 5 routes "Has plan" → `executing-plans`, whose Step 3 is an **unconditional** `REQUIRED SUB-SKILL: finishing-a-development-branch`. The epic-member deltas suppress only the worker's *own* 6.7/6.8 — not the finishing call made *internally* by the downstream skill. At member 1's end the agent sees the epic worktree's named branch and is offered the 4-way merge/PR/cleanup menu → either merges `feat/epic-<id>` to main mid-epic (destroying the one-branch/one-PR invariant and the cumulative-e2e gate, possibly `git worktree remove`-ing the shared worktree later members need) or stalls. `subagent-driven-development` has the same DOT terminus. The orchestrator's "Merging members individually" warning names the failure but enforces nothing.
**Fix:** Add an explicit Step-5 epic-member delta: when routing to `executing-plans`/`subagent-driven-development`, drive only their Execute-Tasks step and STOP before their Complete-Development/finishing handoff, returning control to the orchestrator (member is done at commit-on-branch + per-member integration green). Mirror for both skills.

### 3. E6 batched-e2e failure has no recovery path — orchestrator stalls at its own headline gate
**Where:** `backlog-next-epic/SKILL.md` E6 (96–115), E7 step 2 (120) — dimension: epic-flow-trace.
**Why:** E6 specifies flake-confirmation and "e2e gap is queued not parking," but nothing tells the orchestrator what to do with a *hard, reproducible* e2e failure: no route to systematic-debugging (E4.3 covers only per-member integration), no procedure to localize which member's co-mingled change regressed (the fault-isolation rationale is lost at the batched gate), no re-open/abort. Worse, E7 gates the ship on `epic-members.mjs exit 10` (member terminality) only — drainable can be true while e2e is red, and E7.3 then cites "batched-e2e evidence" that didn't pass. Spec lines 88–96 have the identical omission.
**Fix:** Add an E6 failure branch: confirmed (non-flake) failure → `superpowers:systematic-debugging`; if root cause maps to a shipped member, re-open it (active, fix on branch, re-run its integration) and return to E6; if a new gap, file `queued` via backlog-add as an epic member and loop to E4. State that E7's rule-9/exit-10 check is necessary but **not sufficient** — green batched e2e is the second precondition for E7.3.

### 4. `--auto` cannot mechanically override AskUserQuestion prompts raised inside sub-skills
**Where:** `backlog-next-epic/SKILL.md` E5 (83–94), E8.1 (126) → `superpowers:brainstorming` / `finishing-a-development-branch` — dimension: auto-safety.
**Why:** The real decisions aren't raised by the orchestrator — they're raised *inside* downstream skills it has no mechanism to intercept. (a) `brainstorming` carries a `<HARD-GATE>` ("Do NOT … until the user has approved … EVERY project regardless of perceived simplicity"); a `type: design` member routes here and `--auto` neither satisfies nor bypasses it — the agent stalls, or self-approves and violates the gate. (b) `finishing-a-development-branch` (E8.1) always presents a 4-option menu ending "Which option?" — an operational prompt that isn't an "architectural fork," so E5's (Recommended)-pick rule doesn't apply and it's not on the hard floor; it falls through entirely. These are `--auto`'s two most common blocking points, so the gap materially undercuts the headline feature.
**Fix:** Add named E5 decision categories with explicit auto-resolutions: document that `--auto` pre-selects finishing Option 2 (Push+PR) and answers that menu without pausing; and either declare `type: design` members not `--auto`-eligible (always pause) or specify how the brainstorming hard-gate is satisfied (present design to the decision log + self-approve). A catch-all — "any sub-skill prompt not enumerated here is treated as floor (pause)" — closes the residual taxonomy gap (see Should-fix).

### 5. The flat-section picker can grab an epic member directly, bypassing the orchestrator
**Where:** `backlog-lint/lib/index-render.mjs` (102–145) + `backlog-next/SKILL.md` Step 1 (33–37) — dimensions: preexisting-health (raised to major) + worker-skill-coherence.
**Why:** `renderIndex` builds ACTIVE/QUEUED/LATER from the full nonEpic set with no exclusion for live-epic members, so a queued member is double-listed (rollup + flat QUEUED). The worker's pick redirects only on `type: epic` — an epic *member* is a non-epic file with an `epic:` pointer, so the redirect never fires and `ruleQueuedRanks` lets it be the lowest-rank pick. A bare `/backlog-next` can therefore select a queued epic member and work it standalone (own branch/PR/e2e), defeating the one-branch/one-PR/batched-e2e design. This compounds with worker default-pick #1 (Should-fix below). Note: this renderer code is preexisting/untouched by the diff, but the new split is what makes the gap load-bearing.
**Fix:** Make the decision explicit — exclude live-epic members from the flat sections (rollup canonical) and/or add a worker Step-1 guard: if the picked item has an `epic:` pointer to an `active` epic, redirect to `/backlog-next-epic <epic-id>` rather than working it standalone.

## Should-fix (minor, confirmed-real)

- **Worker default-pick #1 still narrates epic "delivery epic / in-flight member" logic** the worker disowned (`backlog-next/SKILL.md:33`). Contradicts the design spec's explicit removal directive and creates a wrong-mode-resume hole (bare `/backlog-next` mid-epic resumes a member in *standard* mode → premature PR/cleanup). Fix: drop the epic parenthetical, or guard `epic:`-pointered active members to redirect. *(Pairs with Must-fix #5.)*
- **BACKLOG.md regenerated on both main (E1) and branch (E4/E7)** → guaranteed merge-conflict surface at E8 when a parallel `/backlog-next` doc/simple workstream commits a regen to main (CLAUDE.md explicitly permits this). E8 routes to finishing with no conflict note. Fix: add an E8 note that a `docs/BACKLOG.md` conflict is expected and resolved mechanically (take branch side, re-run `lint --fix` on the rebased branch, never hand-merge). *(Same root cause underlies the E1/E2 promotion-marker finding and the backlog-add-mid-epic finding — all three are the dual-write-of-the-auto-index hazard; one E8 note + one E4/E5 fold-in note covers them.)*
- **E6 e2e scoping is underspecified** — "scoped to the flows the epic touched" but the commands shown are the full unscoped suite, no resolver, and no cross-reference to `[feedback_e2e_nx_wrapper_strips_quotes]` (regex scoping → exit 0, zero tests, false green). Fix: either accept full-suite for the epic gate (defensible — cost amortized) or document env-var scoping; at minimum cite the strips-quotes feedback so an agent doesn't hand-write a `--testPathPatterns` regex.
- **E7.4 attributes the captured-member spin-out to `lint --fix`, but the code doesn't do it.** `lint.mjs --fix` only regenerates BACKLOG.md + dossiers; `ruleEpicClosure` only *blocks* (emits a violation), it creates no `<id>-leftovers` file and repoints nothing. An agent running E7 with open captured members hits the rule-9 blocker with no automated remedy. Fix: either make `lint --fix` actually create the leftovers epic + repoint members, or rewrite E7.4 so the orchestrator explicitly creates `<id>-leftovers` and moves each captured member's `epic:` pointer *before* `--fix`.
- **`--auto` per-member "bounded effort" debugging pause has no defined bound** (E4.3) — no iteration cap/time box, contradicting the same skill's explicit ≥5-e2e-runs cost floor (E6). An auto-debug loop can burn dev deploys + mocked integration runs + wall-clock unbounded (note: per-member runs are deploy+integration, *not* e2e/AgentCore). Fix: define a concrete cycle/time bound and make "bounded effort exceeded" a named E5 floor item.
- **E1 drainable-before-work short-circuit skips E6 but E7.3 still requires batched-e2e evidence** — an already-drainable epic ships claiming evidence never produced (and lint rule 5 forces *something* into validation_gate → likely fabricated). Fix: route the short-circuit to E6 (run batched e2e on the cumulative state), or have validation_gate cite per-member evidence and explicitly note no cumulative e2e ran.
- **Run-state duplicates member status with frontmatter and states no precedence** (E3/E9). Member status has a code-derived single source (`epic-members.mjs`); run-state mirrors it by hand with no "frontmatter wins" rule. Impact is bounded (selection/termination read frontmatter, not run-state), but it invites drift. Fix: drop `members` from run-state (keep it for decision log + e2e evidence only) and state "frontmatter wins; run-state is append-only annotation."
- **Non-architectural operational prompts fall through E5's binary taxonomy** (fork vs floor). Of the four cited cases, only the finishing merge-menu is genuinely reachable in epic-member mode (the worktree-phantom and lane-upgrade cases are neutralized by epic-member deltas). Fix: the one-clause catch-all from Must-fix #4 ("any sub-skill prompt not enumerated → treat as floor/pause") closes it.

## Needs your decision

- **Should the `--auto` hard floor get a *mechanical* backstop, or stay advisory-only?** (E5 floor, line 91; "Common mistakes" line 154 — auto-safety.) The floor is pure prose enforced by the same agent `--auto` has primed not to pause; preflight/postflight are the only mechanical gates and neither knows about `--auto`. Mitigant: the worst-named ops (`push --force`, `branch -D`, `reset --hard`, non-dev AWS mutations) are *already* gated by the harness/CLAUDE.md confirmation layer, so the floor isn't the sole defense for those. The choice: (a) add a run-state-aware guard the orchestrator sources that refuses those ops when `auto:true`, or (b) explicitly label the floor advisory-only so you calibrate trust. Cheapest defensible minimum is (b). This is a trust-boundary call you own.
- **Worker bare-`/backlog-next` epic-member guard — fix or accept?** (`backlog-next/SKILL.md:33–37` — worker-skill-coherence.) Largely subsumed by Must-fix #5/Should-fix #1, but note line 33 *deliberately* says "resume either way," and the only way a bare pick lands on a member is running from *inside* the epic worktree (worst case: an over-eager finish on an already-correct worktree, not data loss). Decide whether to add the `epic:`→active-epic redirect guard or accept the documented "either way" behavior.

## Nits / optional

- `epic-members.mjs` rolls its own line-regex frontmatter parser instead of importing the canonical `backlog-lint/lib/frontmatter.mjs` (real `yaml`). No live mis-read today (the only divergence, `rank: null`→`"null"`, is unreachable: no file is both `queued` and `rank:null`), but it's a dual-source-of-truth maintenance hazard and the **fourth** independent fence-regex parser in the backlog toolchain (canonical lib + epic-members + postflight.mjs — note `rules.mjs` consumes pre-parsed frontmatter, it doesn't parse). Fix: import `parseFrontmatter`/`loadBacklogFiles` from the lint lib; drops the `Number(rank)` coercion + quote-stripping too.
- `epic-members.test.mjs` doesn't exercise the string→number rank coercion end-to-end (string ranks via `parseFrontmatter`→`coreMembers`, e.g. `'10'` vs `'2'`) or multi-active determinism. Runtime is correct; coverage hardening only.
- **Postflight check-3 asymmetry**: standard Step 7 omits `--id` so the shipped-frontmatter check silently no-ops, yet epic-member mode passes `--id` and gets the stricter check; line-164 prose claims it always hard-fails. Pre-existing, widened by this change. The dangerous half (empty `validation_gate`) is still caught by lint rule 5. Fix: pass `--id` in standard Step 7 too, or soften line 164.
- Stale `/backlog-next Step 1a.5` reference in `docs/superpowers/plans/2026-06-18-typed-test-fixtures-phase4-ledger.md:411` (Step 1a was removed). Harmless — referencing plan's epic is `shipped`. Leave for provenance or annotate that epic-ship now lives in `/backlog-next-epic` E7.
- Add one line to the epic-member intro: "Step 1 (Pick) does not run — the orchestrator passes the member id; the worker starts at Step 1b" (makes the only undocumented step omission intentional).
- Decision-log schema specified twice (E5 superset `{member, decision, options, chosen, rationale, rejected}` vs spec subset). Pick E5 as canonical and reference it from E3/spec.
- Decision-log→PR-body mechanism under-specified: E8.1 asserts "PR body = decision log," but `finishing-a-development-branch` Option 2 only `git push`es (no body composition). Specify that the orchestrator renders `decisions[]` to markdown and creates the body (`gh pr edit --body-file`), plus empty-log wording. Mirrors existing worker convention, so low-impact.
- **Preexisting (not in diff):** rule-3 anchor validation scans fenced code blocks, so `# shell comments` register as resolvable headings (false-positive resolution only — never wrongly rejects). And a parking member pointing at a *shipped* epic is excluded from the orphan count and every rollup, going invisible to triage (rule 9 normally prevents this; only reachable via post-ship re-open). Both are out-of-scope for this merge but worth a follow-up backlog item.

## Notable strengths
- `epic-members.mjs` is the standout: pure exported functions, only `node:` imports, clean `import.meta` CLI guard, 9 passing tests, deterministic ordering matching the prose, and status/role classification that exactly mirrors the frozen lint model (`OPEN_STATUSES` = complement of `TERMINAL`; `epic_role || 'core'`). It lifts as-is into any repo adopting the backlog model — the strongest reusable artifact in the change.
- Epic-member mode delta coverage is complete: every standard worker step (0, 1b, 2, 3, 4, 5, 6.1–6.8, 7) has an explicit verdict, with Step 1 correctly the only omission (orchestrator supplies the id).
- The `--auto` decision-log-as-async-review concept is a genuinely good, reusable idea; the gaps are in wiring/enforcement, not the design.
